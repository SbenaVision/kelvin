## Recommendations on the three open questions

### Q1 — Score model: numeric 1–10 vs three categories

**Recommendation: Numeric 1–10 *plus* derived category, both shown.**

The default output displays:
```
Maturity Score: 4 / 10
Verdict: Not production-ready
```
The number gives information density and lets us say "expected after fix: 7/10". The category gives a sanity check that absorbs calibration squish — if 5 vs 6 isn't meaningful, the category bucket (Not ready / Needs work / Production-ready) still is.

Bucketing convention:
- **1–3 → Not production-ready**
- **4–6 → Needs work**
- **7–10 → Production-ready**

If calibration proves too fragile in practice (acceptance criterion 5 fails on the reference pipelines), the fallback is to *hide* the numeric in default output and show only the category, while still computing the numeric internally. The infrastructure cost of carrying both is small.

### Q2 — What "10" means

**Recommendation: 10 = "behaviorally indistinguishable from a deterministic, rule-tracking, drift-free reference pipeline,"** with a concrete reference pipeline shipped in Kelvin so anyone can verify.

Operational definition for 10:
- η < 0.05 (drift below noise floor)
- Sens_cal in correct direction on every rule-bearing axis with margin ≥ 0.30
- R_eq holds at hold-rate ≥ 0.99 on order / optional / non-rule axes
- No wrong-direction sensitivity on any axis

Ship reference pipelines under `kelvin/reference_pipelines/`:
- `constant.py`              → score 1
- `brittle.py`               → score 2
- `mid_issue.py`             → score 4
- `one_moderate_issue.py`    → score 7
- `grounded_oracle.py`       → score 10

Each reference pipeline is a tiny standalone Python module that Kelvin can run against itself. They give users fixed points and let us write a calibration test that hard-asserts the score ordering.

This is **better than Envelop-as-anchor** because Envelop is a real (eventually-LLM-backed) pipeline whose score may drift as the underlying model changes. The reference pipelines are deterministic Python — their score should never move.

### Q3 — Variance decomposition: ANOVA or top-3-by-impact

**Recommendation: Top-3-by-impact in default output, ANOVA-style detail in `--verbose`.**

Default output ranks perturbation categories by score-loss contribution and reports the top 3:
```
Top contributors to score loss:
  1. Rule axes (drift on rule-text changes):    -3 points
  2. Stochastic noise (different answers):       -2 points
  3. (everything else)                           -1 point
```

`--verbose` adds the ANOVA-style decomposition:
- % of variance explained per category
- F-stat (or analog) per perturbation family
- residual / unexplained variance

Why this split:
- **Top-3-by-impact** is what feeds the "Top fix" line. It needs to be plain-language, robust to unbalanced design (which we have — different families fire on different cases), and direct.
- **ANOVA** is rigorous but assumes a factorial layout we don't always have. Better as supplementary detail than primary output.

The math underneath is the same: for each perturbation category, compute the per-case contribution to (1 − Sens_cal) or |Inv_cal − 1|, sum across cases, rank. Top-3-by-impact reports the sums; --verbose reports the variance decomposition.

## Implementation order

Phased over ~14 working days. Each phase produces a testable artifact.

### Phase 1 — Foundation (days 1–3)

**Goal:** the substrate the rest of v0.4.0 depends on.

1. **Day 1.** `taxonomy.py` — perturbation categories. Each existing family is mapped to one category. Tests: `pytest tests/test_taxonomy.py` passes; every family in `PerturbationKind` has a category.
2. **Day 2.** `reference_pipelines/{constant,brittle,mid_issue,one_moderate_issue,grounded_oracle}.py` — five anchor pipelines, runnable via `kelvin check`. Tests: each runs to completion against the existing `cases/` corpus and produces a `RunScores` object.
3. **Day 3.** `isotonic.py` — pure-stdlib isotonic regression utility. Tests: known monotone / non-monotone toy data.

**Phase 1 ships:** the reference-pipeline harness used to calibrate score in Phase 2.

### Phase 2 — Score model (days 4–7)

**Goal:** `MaturityScore` correctly orders the reference pipelines.

4. **Day 4.** `score.py` skeleton: anchor table + per-axis sub-scores + min-aggregation. No calibration yet.
5. **Day 5.** Calibration loop: iterate parameter set on the five reference pipelines until each anchor scores its target ± 0.5. Test: `tests/test_reference_pipelines.py::test_anchors_calibrated` passes.
6. **Day 6.** Cross-check on v2.1 / v2.2 pipelines (f_track, f_wrongstatic, f_wrongstochastic, f_ruleblind, f_constant). They should score in the correct order: track ≥ 7, wrongstochastic ∈ [3, 5], wrongstatic / ruleblind / constant ≤ 3. Test: `tests/test_score.py::test_v21_pipelines_ordered` passes.
7. **Day 7.** Score-stability tests: same pipeline, repeated runs, score within ±1.

**Phase 2 ships:** the maturity score that everything else hangs off.

**This is the squishiest phase.** Risk assessment below.

### Phase 3 — Findings + recommendations + variance (days 8–10)

**Goal:** plain-language explanations and actionable fixes.

8. **Day 8.** `findings.py` — curated rules table. ~10–15 rules covering: drift, rule-blindness, wrong-direction sensitivity, ignored-fields, brittle-to-presentation, stochastic instability, etc. Each rule has plain-English text and severity. Test: each rule fires when its conditions are met on synthetic data.
9. **Day 9.** `recommendations.py` — 5–7 fix patterns. Each maps a finding (or set of findings) to an actionable recommendation with an *expected score gain*. The score gain is computed by simulating "what if this finding's metrics improved to threshold X?" Test: each rec fires when its symptoms match.
10. **Day 10.** `variance.py` — top-3-by-impact ranking. Per-category contribution to score loss. Tests: synthetic data with known dominant axis is ranked correctly.

**Phase 3 ships:** the explanation + recommendation pipeline.

### Phase 4 — Reporters + CLI (days 11–13)

**Goal:** the user-facing surface.

11. **Day 11.** `reporters/practitioner.py` — the 30-second box. Snapshot tests against each reference pipeline.
12. **Day 12.** `reporters/json.py` and `reporters/markdown.py`. Tests: schema validation + snapshot.
13. **Day 13.** CLI rework: `--verbose`, `--research`, `--report-format`, `--version`. Rename `terminal.py` → `research.py`. Wire everything together.

**Phase 4 ships:** end-to-end `kelvin check my_pipeline.py` works for a real user.

### Phase 5 — Docs + ship (day 14)

14. **Day 14.** README rewrite. `docs/methodology.md` transplant. CHANGELOG. `kelvin --version` smoke test. TestPyPI release. PyPI release.

## Test strategy

Six layers, each independently runnable.

### 1. Unit tests per module

Each new module gets a `tests/test_<module>.py` with focused unit tests. Existing v0.3.0 unit tests stay untouched (no API regression).

### 2. Reference-pipeline calibration test (acceptance criterion 5)

`tests/test_reference_pipelines.py::test_anchors_calibrated` — runs all five reference pipelines through `kelvin check` and asserts each scores its target value ± 1.

`tests/test_reference_pipelines.py::test_v21_pipelines_ordered` — runs the v2.1 / v2.2 reference pipelines and asserts the score order:
```
constant ≤ ruleblind ≤ wrongstatic ≤ wrongstochastic ≤ track
```

### 3. Snapshot tests for default output (acceptance criteria 1–4)

`tests/test_reporters_practitioner.py` golden-files the default output box for each reference pipeline. Hand-inspected once, frozen as `tests/snapshots/<pipeline>.txt`. Future changes that break the box format require explicit snapshot update.

### 4. JSON / markdown schema validation

`tests/test_reporters_json.py` — JSON output validates against a schema in `tests/schemas/practitioner_v1.json`.

`tests/test_reporters_markdown.py` — markdown output is parseable and contains required sections.

### 5. Research-mode regression test (acceptance criterion 6)

`tests/test_research_mode.py` — `kelvin check --research` against the v0.3.0-era cases produces output that matches a v0.3.0-era snapshot byte-for-byte (modulo the new bootstrap-CI fields, which are explicitly opted-in).

This is the contract that says "v0.3.0 functionality is preserved."

### 6. End-to-end test (acceptance criterion 1)

`tests/test_e2e_practitioner.py` — simulates `pip install kelvin-eval && kelvin check my_pipeline.py` workflow. Checks: command runs to completion, output prints to stdout, exit code reflects pipeline maturity (0 for production-ready, 1 for needs-work, 2 for not-ready).

## Risk assessment for the score-calibration step

This is the squishiest part of v0.4.0 and the highest single risk. Five risks ranked by severity:

### R1. Calibration overfit (HIGH)

**Risk:** we tune the score function until the five reference pipelines hit their targets, but the score is then meaningless on new pipelines.

**Mitigation:**
- Calibrate ONLY on the five reference anchors, but VALIDATE on the v2.1 / v2.2 pipelines (which we did NOT tune to). If validation fails, the score function is overfit.
- Keep the score function simple — anchor-interpolation + min-aggregation, not a learned model. No more than 3–5 free parameters.
- Document every calibration knob in `score.py` and gate "calibration mode" behind a test-only flag so it can't accidentally drift in production.

**Trigger to fall back to category-only:** if the v2.1 / v2.2 cross-check fails, switch the default output to category labels (`Not production-ready` etc.) and emit the numeric only in `--verbose`.

### R2. Score regime depends on enabled families (MEDIUM-HIGH)

**Risk:** a user runs with `intra_slot.enabled=False` and sees a different score than a user who enables it. Same pipeline, different score → confusing.

**Mitigation:**
- Score is computed against a STANDARD family set (rule-bearing axes + order + optional + drift). If the user disables one of these, Kelvin warns: "Maturity score requires the standard family set; running with reduced families. Score withheld; use --research for raw metrics."
- The standard family set is documented and pinned in `config.py` as `STANDARD_SCORE_FAMILIES`.
- A user who DISables a standard family explicitly opts out of the maturity score.

### R3. Adversarial gaming (MEDIUM)

**Risk:** a user tunes their pipeline's prompts until Kelvin scores 10, without actually being more reliable. (Kelvin is then a metric to game, not a diagnostic.)

**Mitigation:**
- Document explicitly: "Kelvin scores what Kelvin tests. It is not a substitute for production monitoring."
- The variance decomposition makes gaming harder: a pipeline that games by hardcoding outputs will be flagged by `f_constant`-pattern detection (low Sens across the board).
- Long-term mitigation lives in v0.5.0+: rotating perturbation set, sealed catalogue (the EOS work).

### R4. Disagreement between metrics (MEDIUM)

**Risk:** K_cal says good, but Sens_cal says bad. What's the score?

**Mitigation:** **MIN-aggregation.** The score is the min across per-axis sub-scores. A pipeline that drifts heavily can't score above the drift sub-score. This is conservative — if any axis is broken, the pipeline isn't production-ready, regardless of how clean the others are.

Pseudocode:
```
sub_score_drift = anchor_interp(η)
sub_score_rule_axes = anchor_interp(min_correct_direction_rate_on_rule_axes)
sub_score_invariance = anchor_interp(max_violation_rate_on_invariance_axes)
sub_score_stochastic = anchor_interp(stochastic_instability_metric)
maturity_score = min(sub_score_drift, sub_score_rule_axes,
                     sub_score_invariance, sub_score_stochastic)
```

### R5. Anchor pipelines drift over time (LOW)

**Risk:** the reference pipelines' scores shift as Kelvin's measurement code evolves.

**Mitigation:**
- Each reference pipeline is a frozen Python module. Score-anchor tests run on every CI build.
- If a Kelvin code change causes the constant.py reference to score 1.7 instead of 1.0, the test fails. Forces a conscious decision: was the change intentional?

### R6. The "expected score after fix" claim might be wrong (LOW–MEDIUM)

**Risk:** "Set temperature=0 → expected score 7/10" — but actually the fix bumps it to 5/10, and the user feels misled.

**Mitigation:**
- Compute "expected after fix" by simulating: replace the offending metric with the threshold value in `RunScores`, recompute the score. This is a math operation, not a guess — but it's optimistic.
- Word the line carefully: "Expected score after fix: ~7 / 10" (with the tilde) — signals it's an estimate.
- Track in v0.5.0 whether actual post-fix scores match predictions; refine if not.
